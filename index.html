本页的学习路线（每一步都解决上一步的痛点）

  1. Dijkstra：正确但盲目——像倒水一样向四周均匀泛洪。
  2. A*：给搜索加"方向感"，用一个不超过真实距离的估计值引导。
  3. 双向搜索：两头同时找，搜索面积减半。
  4. ALT：用预先算好的地标距离给出更紧的下界，A* 更准。
  5. 收缩层次 CH：预处理出"捷径"，查询时只往"更重要的路"爬——这是开源导航引擎的主力方法，查询只碰几百个节点。
  6. 时变权重：边权是时间的函数，早高峰自动绕开高速。

为什么非要这么多花样？量级感受一下

西欧路网约 1800 万节点、4200 万边，单次点到点查询的典型耗时（数量级，取自 Bast 等人 2016 年综述 Route Planning in Transportation Networks，不同硬件会有差别）：

Dijkstra≈ 2 s
双向 Dijkstra≈ 1 s
ALT（地标 A*）≈ 0.1～0.3 s
CH 收缩层次≈ 0.1 ms
Hub Labels≈ 1 μs

条形为对数刻度示意。Dijkstra 要碰上千万节点；CH 只碰几百个。导航 App 每秒要回答成千上万次查询，2 秒一次根本不可用。

1. 道路网 → 带权图

所有算法的输入都是同一个东西：一张图。先把"地图"翻译成数学对象。

定义

$$G=(V,\,E,\,w),\qquad V=\{\text{路口}\},\quad E\subseteq V\times V=\{\text{路段（有向）}\},\quad w:E\to\mathbb{R}_{\ge 0}$$

边权是"代价"。导航最常用耗时：路段长度除以可通行速度

$$w(e)=\frac{\ell_e}{v_e}\qquad(\ell_e\text{ 为路段长度},\ v_e\text{ 为限速或预计车速})$$

一条 \(s\to t\) 的路径 \(P=(s=v_0,v_1,\dots,v_k=t)\) 的代价是边权之和，最短路就是代价最小的那条：

$$\operatorname{dist}(s,t)=\min_{P}\ \sum_{i=0}^{k-1} w(v_i,v_{i+1})$$

权重非负（\(w\ge 0\)）是后面 Dijkstra 正确性的前提——现实中耗时、距离都天然非负。

经纬度 → 距离：Haversine 公式

路段长度来自地图几何；两个经纬度点 \((\varphi_1,\lambda_1),(\varphi_2,\lambda_2)\) 的大圆距离：

$$d = 2R\arcsin\sqrt{\sin^2\!\frac{\varphi_2-\varphi_1}{2}+\cos\varphi_1\cos\varphi_2\sin^2\!\frac{\lambda_2-\lambda_1}{2}}\,,\quad R\approx 6371\ \text{km}$$
→

现实里还要处理的事（本页做了简化）

  • 单行道：边是有向的。本页为了演示简洁按无向图（双向通行）处理，所有算法在有向图上形式不变。
  • 转向限制 / 转向代价（禁止左转、掉头耗时）：标准做法是把"路段"当节点、"允许的转向"当边（边图 / line graph），或在搜索状态里带上"从哪条边来"。
  • 地图匹配：手机 GPS 点并不落在路上，要先用隐马尔可夫模型（HMM）把轨迹"吸附"到最可能的路段序列，再从那个位置出发规划。
  • 多种代价：最快、最短、少收费、少红绿灯……本质是换一个 \(w\)，或做多目标优化。

2. Dijkstra：向四周"泛洪"

1959 年的算法，至今仍是一切路径规划的基准与正确性参照。直觉：从起点倒一杯水，水面总是先淹没"离起点最近"的点。

三条公式就是整个算法

初始化：起点的暂定距离为 0，其余为无穷大

$$d(s)=0,\qquad d(v)=\infty\ \ (v\neq s)$$

取最小：从未确定的节点集合（优先队列 \(Q\)）里取暂定距离最小的，它的距离从此"板上钉钉"

$$u=\arg\min_{v\in Q} d(v)$$

松弛：看能否借道 \(u\) 让邻居更近

$$d(v)\leftarrow\min\big(d(v),\ d(u)+w(u,v)\big)\qquad\forall\,(u,v)\in E$$

碰到终点 \(t\) 被取出时即可停止，此时 \(d(t)=\operatorname{dist}(s,t)\)。

为什么"取出来的就是最终答案"

不变式：每当 \(u\) 被取出，\(d(u)=\operatorname{dist}(s,u)\)。

反证：若存在更短的 \(s\to u\) 路径，它必须在某处第一次离开"已确定集合"，经过某个未确定节点 \(x\)。因为 \(w\ge 0\)，有 \(\operatorname{dist}(s,x)\le\) 这条路径长 \(< d(u)\)；而 \(x\) 的暂定距离已被它的已确定前驱松弛过，所以 \(d(x)=\operatorname{dist}(s,x)<d(u)\)，与"\(u\) 是队列里最小的"矛盾。

复杂度（二叉堆）：

$$O\big((|V|+|E|)\log|V|\big)$$

路网是稀疏图，\(|E|\approx 2.5|V|\)，所以大致是 \(O(|V|\log|V|)\)。问题不在常数，而在它必须把起点周围"一圈"全部搜完——搜索区域面积与 \(\operatorname{dist}(s,t)^2\) 成正比，跨城查询动辄上千万节点。

// 伪代码（二叉堆 + 惰性删除）
d[*] = ∞; d[s] = 0; Q.push(0, s)
while Q 非空:
    (key, u) = Q.pop_min()
    if u 已确定: continue          // 过期堆项
    标记 u 已确定; if u == t: break
    for (u, v, w) in 出边(u):
        if d[u] + w < d[v]: d[v] = d[u] + w; prev[v] = u; Q.push(d[v], v)
优先队列前 5 项（节点 / 暂定距离 min）

观察什么

  • 蓝色"已确定"区域像涟漪一样以起点为中心向外扩，形状是耗时等值线（沿快速路伸得更远），完全不看终点在哪。
  • 用"单步"看松弛：橙色 = 这次松弛让邻居更近了（更新并入队），灰色 = 没有更近（不更新）。
  • 队列里同一个节点可能有多个过期项，弹出时发现"已确定"就跳过——这就是伪代码里的惰性删除。
  • 记住"已确定节点数"这个数字，后面每一节都拿它做对照。

3. A*：给搜索加上"方向感"

Dijkstra 只看"已经走了多远"；A* 再加上"估计还要走多远"，优先扩展总估计最小的节点。

核心公式

$$f(v)=\underbrace{g(v)}_{\text{已走：}d(v)}+\underbrace{h(v)}_{\text{估计还要走}}\qquad u=\arg\min_{v\in Q} f(v)$$

\(h\) 必须是可采纳的（永远不高估）才能保证最优：

$$h(v)\le \operatorname{dist}(v,t)\quad\forall v$$

更强的一致性（三角不等式形式）保证每个节点只需取出一次：

$$h(u)\le w(u,v)+h(v)\quad\forall (u,v)\in E,\qquad h(t)=0$$

耗时权重下最常用的几何启发式：直线距离 ÷ 全网最高限速

$$h(v)=\frac{\|p_v-p_t\|_2}{v_{\max}}$$

任何真实路径都不比直线短、不比最高限速快，所以它永远不高估。

一个漂亮的等价看法

A* 等价于在"改过权重"的图上跑 Dijkstra：

$$w'(u,v)=w(u,v)-h(u)+h(v)$$

一致性恰好保证 \(w'\ge 0\)；任意 \(s\to t\) 路径的新权重 = 旧权重 \(-\,h(s)+h(t)\)，差一个常数，所以最短路不变。朝终点走的边 \(h\) 下降、\(w'\) 变小，于是搜索"被吸向终点"。

加权 A*：用最优性换速度

$$f(v)=g(v)+\varepsilon\,h(v),\qquad \varepsilon\ge 1\ \Rightarrow\ \text{路径代价}\le\varepsilon\cdot\operatorname{dist}(s,t)$$

\(\varepsilon=0\) 退化成 Dijkstra；\(\varepsilon=1\) 是标准 A*；\(\varepsilon>1\) 更贪心、搜得更少，但可能找到稍长的路（误差有界）。下面的滑块可以亲手试。

优先队列前 5 项（节点 / f 值）

观察什么

  • 搜索区域从"圆"变成朝向终点的椭圆，已确定节点数明显少于 Dijkstra。
  • 把 ε 拉到 0 → 和第 2 节一模一样；拉到 2～3 → 几乎直奔终点，但看"相对最优"一栏，路径可能变长。
  • 为什么省得不够多？看统计里的"起点处下界 h(s)"（第 5 节有对照）：直线÷最高限速 远小于真实耗时，因为真实路径大多在 30 km/h 的支路上。下界越松，A* 越接近 Dijkstra。这就是下一步 ALT 要解决的问题。

4. 双向搜索：两头同时找

从起点正向搜、从终点在反向图上搜，两个"涟漪"在中间相遇。面积与半径平方成正比，两个半径减半的圆加起来只有原来的一半。

公式

正向距离 \(d_f\)（从 \(s\)），反向距离 \(d_b\)（从 \(t\)，沿反向边）。每当某条边 \((u,v)\) 被松弛且 \(v\) 已被另一侧触达，就得到一条完整路径，用它更新上界：

$$\mu\leftarrow\min\big(\mu,\ d_f(u)+w(u,v)+d_b(v)\big)$$

终止条件——两个队列的最小 key 之和已经不小于当前最好答案：

$$\min_{v\in Q_f} d_f(v)\;+\;\min_{v\in Q_b} d_b(v)\ \ge\ \mu$$

此时任何尚未发现的路径都至少要经过两侧各一个未确定节点，总长 \(\ge\) 左式 \(\ge\mu\)，不可能更短。

一个常见误区

"两边第一次碰到同一个节点就停"是错的。相遇节点 \(v\) 不一定在最短路上——最短路可能经过另一个还在队列里的节点。所以必须维护 \(\mu\) 并用上面的终止条件。演示里能看到：相遇后往往还要再弹出几个节点才满足终止。

和 A* 结合

可以双向 A*，但两侧的启发式需要"互相一致"（例如用平均化 \(h_f(v)=\tfrac{1}{2}(h(v,t)-h(s,v))\)、\(h_b=-h_f\)）才能保留简单的终止条件。工业实现里更常见的是双向 + 分层（第 6 节）。

观察什么

  • 蓝、红两个区域各自长到一半大小就相遇，总节点数约为 Dijkstra 的 40%～60%。
  • 注意"相遇"日志出现后，"终止判定"未必立刻满足——μ 可能还会被更小的候选更新。

5. ALT：用地标给出更紧的下界

A* 的威力取决于 h 有多贴近真实距离。ALT（A*, Landmarks, Triangle inequality）用预先算好的"到几个地标的真实距离"构造下界，在耗时权重下远比直线距离紧。

预处理：选 k 个地标 \(L\)，对每个地标跑一遍全图 Dijkstra，存下 \(\operatorname{dist}(L,v)\) 与 \(\operatorname{dist}(v,L)\)

查询时由三角不等式得到两个下界：

$$\operatorname{dist}(v,t)\ \ge\ \operatorname{dist}(L,t)-\operatorname{dist}(L,v),\qquad \operatorname{dist}(v,t)\ \ge\ \operatorname{dist}(v,L)-\operatorname{dist}(t,L)$$

取所有地标、两种形式里最大的那个作为启发式：

$$h(v)=\max_{L}\ \max\big\{\operatorname{dist}(L,t)-\operatorname{dist}(L,v),\ \operatorname{dist}(v,L)-\operatorname{dist}(t,L)\big\}$$

它可采纳且一致（\(\max\) 保持这两个性质）。无向图上两式合并为 \(\big|\operatorname{dist}(L,t)-\operatorname{dist}(L,v)\big|\)。

空间：\(k\cdot|V|\) 个距离（有向图再乘 2）；\(k=16\) 时全欧洲约几 GB，可接受。

直觉：地标"在终点背后"时下界最紧

若 \(L\) 在 \(t\) 的正后方，\(v\to t\to L\) 近似共线，则 \(\operatorname{dist}(v,L)-\operatorname{dist}(t,L)\approx\operatorname{dist}(v,t)\)，下界几乎等于真值。所以地标要分散在地图边缘：最简单的最远点法——每次挑离现有地标最远的点。更好的 avoid 法会挑"当前下界最差的区域"。

本页用最远点法选地标；统计里对比了起点处的 ALT 下界与欧氏下界各占真实耗时的百分比。

在真实系统里

GraphHopper 的 "LM" 模式就是 ALT；它的优点是权重改了只需重算地标距离（分钟级），比 CH 的预处理灵活，查询则慢一些。

观察什么

  • 紫色菱形是地标。打开热力图对比第 3 节：ALT 的 h 沿着道路变化（它来自真实路网距离），欧氏的 h 是同心圆。
  • 地标 1 个 → 8 个，已确定节点数如何变化？多到一定程度收益递减，但每次查询计算 h 的代价线性增长。
  • 试着把终点放到地标附近 / 远离所有地标，看下界占比的变化。

6. 收缩层次（Contraction Hierarchies）：预处理出"捷径"

2008 年 Geisberger 等人提出，OSRM、GraphHopper 等开源导航引擎的默认算法。思想来自一个常识：远途路线几乎总是"先上主路、走高速、再下到支路"——路网是有层次的。

两阶段

预处理（离线，分钟级）给所有节点排一个"重要性"顺序，从最不重要的开始逐个收缩：把它从图里拿掉，若这破坏了某两个邻居之间的最短距离，就在它们之间补一条捷径边。 查询（在线，亚毫秒）双向 Dijkstra，但只允许走向更重要（更晚收缩）的节点。两侧在"高处"相遇，再把路径里的捷径递归展开成真实路段。

收缩一个节点 \(v\)

对 \(v\) 的每一对（尚未收缩的）邻居 \(u,w\)，比较"经过 \(v\)"与"不经过 \(v\)"的最短距离：

$$\text{若}\quad \operatorname{dist}_{G\setminus\{v\}}(u,w)\ >\ w(u,v)+w(v,w)\quad\text{则加捷径}\ (u,w),\ \ w(u,w)=w(u,v)+w(v,w)$$

左边的"不经 \(v\) 的最短路"叫见证路径（witness），用一个范围很小的局部 Dijkstra 搜（搜不到就保守地加捷径——只会多加，不会错）。

节点顺序：边差（edge difference）

$$ED(v)=\#\text{需加的捷径}-\#\text{与 }v\text{ 相连的边}$$

优先收缩 ED 小的（拿掉它"图变简单"），再加上"已收缩邻居数"等项让收缩在空间上均匀展开。顺序用惰性更新的优先队列维护：弹出后重算优先级，若已不是最小就放回去。

查询：只向上

记 \(\pi(v)\) 为 \(v\) 的收缩次序（rank，越晚收缩越大）。向上图：

$$G^{\uparrow}=\{(u,v)\in E\cup S:\ \pi(u)<\pi(v)\}\qquad(S=\text{捷径集})$$

正向在 \(G^{\uparrow}\) 上从 \(s\) 搜，反向也在 \(G^{\uparrow}\) 上从 \(t\) 搜（有向图时用反向边）：

$$\mu=\min_{v}\ d_f^{\uparrow}(v)+d_b^{\uparrow}(v)$$

某一侧队首 key \(\ge\mu\) 时该侧停止。

为什么不会漏掉最短路

定理：任意最短路都能表示成一条先上升后下降的路径（中间可含捷径）。归纳：取最短路上 rank 最低的内部节点 \(v\)，它被收缩时要么它两侧邻居间有不经过它的等长见证路径（可替换），要么已经加了捷径——两种情况都能把 \(v\) 从路径里消掉而不变长。反复消掉局部最低点，剩下的就是单峰的上-下路径。

6.1 八个节点的玩具图：一步一步看收缩与查询

观察什么

  • 预处理动画里，支路上的节点先被收缩（ED 低），快速路上的节点最后才收缩——"重要性"顺序是算法自己从结构里学出来的，没有人工标注道路等级。
  • 查询阶段节点半径 ∝ rank。两侧搜索都"向上爬"，确定的节点数只有 Dijkstra 的一小部分；绿色虚线弧是路径里的捷径，日志里能看到它们被逐条展开。
  • 换一对起终点再查：预处理不用重做——这正是 CH 的价值，也是它的软肋：边权一变（比如实时路况），捷径就可能失效，需要重新预处理。

同一家族的其他工业方法（了解名字即可）

  • CRP / Customizable Route Planning（Delling 等，微软）：把路网多级分区，预处理只依赖拓扑；换一套权重（路况、车型）只需几秒"定制"。Bing Maps 与 OSRM 的 MLD 模式用它。适合权重经常变的场景。
  • Hub Labeling：给每个节点存一张"枢纽标签"表，查询只是两张表的合并，微秒级，但空间大。
  • Transit Node Routing：长途查询只经过少数"中转节点"，查表即可；短途回退到 CH。
  • Google Maps 没有公开其引擎细节；从公开资料看，它同样属于"分层/分区预处理 + 双向查询"这一族，再叠加实时路况与机器学习的 ETA 预测（见下一节）。

7. 实时路况：边权是时间的函数

早高峰的高速可能比支路还慢。导航系统把每条路段的车速做成一天内的曲线（历史统计 + 实时探针 + 预测），路径规划变成"时变最短路"。

时变最短路

边权依赖于进入该边的时刻 \(\tau\)：

$$w_e(\tau)=\frac{\ell_e}{v_e(\tau)}$$

标签改为"到达时刻"，松弛时按到达 \(u\) 的时刻取权重（出发时刻 \(\tau_0\)）：

$$a(s)=\tau_0,\qquad a(v)\leftarrow\min\big(a(v),\ a(u)+w_{uv}(a(u))\big)$$

只要满足 FIFO 性质（先出发不会后到达，即"在路上等一等"没有好处）：

$$\tau_1\le\tau_2\ \Rightarrow\ \tau_1+w_e(\tau_1)\ \le\ \tau_2+w_e(\tau_2)$$

Dijkstra 的"取出即最终"不变式仍然成立，算法可以原样使用。本页的速度曲线变化平缓，满足 FIFO（等价于 \(w_e'(\tau)\ge -1\)）。

数据从哪来，ETA 怎么算

  • 历史曲线：按星期几、每 5～15 分钟一档，统计每条路段的典型车速。
  • 实时探针：开着导航的手机匿名上报位置，推算当前车速，覆盖最近几分钟。
  • 预测：你 40 分钟后才到的那段路，要用的是 40 分钟后的车速。Google Maps 与 DeepMind 在 2020 年公开过用图神经网络（GNN）预测路段未来车速，将 ETA 误差降低了数十个百分点。
  • 与预处理结合：CH 需要固定权重，所以实际系统要么做时变 CH（TCH），要么用 CRP 这类"秒级定制"的方法，要么用静态层次做候选、再用时变权重重估。

路段颜色：黄→红 = 此刻越堵（倍率 m 越小）；绿 = 该时刻的时变最短路；灰虚线 = 畅通时的最短路（若两者不同）。悬停路段看此刻耗时。

观察什么

  • 把滑块拖过 8:30 / 18:00：快速路变红，绿色路线离开快速路、改走支路；拖到深夜，又回到快速路。
  • "畅通最短路此刻实际耗时"减去"时变最短路"就是改道省下的时间——这正是实时导航的价值。
  • 注意算法并没有变，变的只是权重函数：这就是把"建模"和"算法"分开的好处。

继续深入可以看的方向

  • 替代路线：找几条"足够不同又足够短"的路（plateau 法、惩罚法）。
  • 多目标：时间 / 距离 / 过路费的帕累托最短路；或把它们线性加权成一个 \(w\)。
  • 公共交通：时刻表不是图上的静态边，用 RAPTOR、Connection Scan 这类专门算法。
  • 偏航重算：离开路线后要在几十毫秒内重算——又是 CH 这类亚毫秒查询的用武之地。
